# 需求文档

## 简介

`project-doc-tracker` 不再被定义为一个可复制到任意项目的单文件 Python 库，而是一个**面向 AI 代理的项目进展跟踪 skill**。它的目标是帮助 AI 在开发过程中持续整理项目进展、决策、阻塞项和下一步动作，降低长期协作中的遗忘风险。

该 skill 采用以下结构：

- `SKILL.md`：定义触发条件、工作流、判断规则和使用约束
- `scripts/project_tracker.py`：负责稳定的文档初始化与写入
- `references/`：存放跟踪格式、数据模型和工作流补充说明
- 项目内追踪数据目录：`docs/project-tracker/`
- 正式文档协作对象：`professional-markdown`

核心思想：

- **skill 负责流程**：AI 决定何时初始化、何时采集证据、何时更新记录
- **script 负责确定性写入**：避免每次手写 Markdown 结构和替换逻辑
- **轻量卡片负责长期记忆**：把阶段性进展、决策、阻塞和下一步动作沉淀下来
- **正式长文档复用专业 skill**：成熟模块的详细文档交给 `professional-markdown`
- **不侵入项目规则文件**：默认不自动改写 `AGENTS.md`、`CLAUDE.md`、`.cursorrules` 等

---

## 术语表

- **Skill**：`project-doc-tracker` 的技能目录，包含 `SKILL.md`、`scripts/` 和 `references/`
- **Tracker Root**：项目中的 `docs/project-tracker/` 目录
- **OVERVIEW.md**：项目级概览，展示当前活跃事项、状态、下一步和最近更新时间
- **PROGRESS.md**：追加式会话日志，记录每次变更的摘要和证据
- **Feature Note**：某个功能或专题的轻量说明卡片，位于 `docs/project-tracker/features/`
- **Formal Doc**：成熟功能或模块的正式长文档，通常位于 `docs/modules/`，由 `professional-markdown` 生成
- **Evidence**：AI 用于推断进展的证据，如 `git diff`、变更文件、`.kiro/specs/`、任务清单、用户最新指令
- **Confidence**：AI 对当前记录结论的信心级别，取值 `high` / `medium` / `low`

---

## 需求

### 需求 1：Skill 触发与使用边界

**用户故事：** 作为开发者，我希望在项目推进、暂停、恢复或回顾时调用一个 skill，让 AI 帮我整理当前项目进展，而不是只提供一个底层库函数集合。

#### 验收标准

1. Skill 的 `description` 必须明确说明它用于项目进展跟踪、阶段总结、恢复上下文和防遗忘场景。
2. Skill 必须覆盖至少以下触发场景：
   - 初始化项目跟踪目录
   - 一次开发会话结束后记录进展
   - 长时间未跟进后恢复项目上下文
   - 某个功能完成后生成轻量说明或正式文档
   - 查询当前状态和下一步
3. Skill 必须在 `SKILL.md` 中定义清晰工作流，而不是只列出脚本命令。
4. Skill 必须说明它不会凭空编造进展；在证据不足时应记录“待确认”或低置信度状态。

---

### 需求 2：初始化项目跟踪文档体系

**用户故事：** 作为开发者，我希望在项目内初始化一个统一的跟踪文档体系，以便后续所有进展、决策和功能说明都有稳定归档位置；如果项目已经有一定代码基础，初始化过程还应自动补全初始概览和关键功能卡片，而不是只创建空文件。

#### 验收标准

1. 这里的“初始化”必须被明确解释为“初始化项目跟踪文档体系”，而不是安装依赖、初始化数据库、启动服务或运行测试。
2. 初始化时应创建 `docs/project-tracker/` 目录。
3. 初始化时应创建 `docs/project-tracker/OVERVIEW.md`。
4. 初始化时应创建 `docs/project-tracker/PROGRESS.md`。
5. 初始化时应创建 `docs/project-tracker/features/` 目录。
6. 若目标文件已存在，初始化过程必须幂等，不覆盖已有内容。
7. 若未传入项目路径，则应默认使用当前工作目录。
8. 若项目已经存在有意义的代码或 spec，初始化流程不应只留下空模板；Skill 应补全初始 `OVERVIEW.md` 内容，并为主要模块创建或更新基础 feature notes。
9. 若项目已经存在成熟模块，初始化流程应至少标记出正式文档候选，必要时建议后续使用 `professional-markdown` 补齐正式文档。

---

### 需求 3：基于证据采集项目进展

**用户故事：** 作为开发者，我希望 AI 在写入项目进展前，先检查当前项目证据来源，尽量基于事实归纳，而不是依赖记忆或猜测。

#### 验收标准

1. Skill 在记录进展前，应优先检查以下至少一种证据来源：
   - `git status` / `git diff`
   - 最近修改的文件
   - `.kiro/specs/` 下的需求、设计、任务文件
   - 用户当前指令和最近目标
2. 若找到多个证据来源，Skill 应优先使用与当前任务最相关的证据。
3. 若证据不足以确认结论，Skill 应将该记录标记为低置信度或“待确认”。
4. Skill 不得仅因为调用了脚本就跳过证据采集步骤。

---

### 需求 4：追加式会话日志

**用户故事：** 作为开发者，我希望每次开发会话结束后都能追加一条结构化日志，以便保留真实时间线并减少遗忘。

#### 验收标准

1. 每次记录进展时，必须向 `PROGRESS.md` 追加一条新记录，不覆盖历史记录。
2. 每条记录至少应包含：
   - 时间戳
   - 变更类型
   - 摘要
   - 关联事项或功能 ID（若已知）
   - 涉及文件（若有）
   - 下一步（若可推断）
   - 阻塞项（若存在）
   - 置信度
3. 变更类型至少支持：`feature`、`bugfix`、`refactor`、`docs`、`research`、`decision`。
4. 历史记录默认采用**只追加，不删除**的审计模型。
5. 若需要纠正旧记录，应追加一条更正记录，而不是直接删除旧记录。

---

### 需求 5：维护项目级概览

**用户故事：** 作为开发者，我希望 AI 在记录进展的同时维护一个可快速浏览的总览页，以便随时知道项目现在卡在哪里、下一步是什么。

#### 验收标准

1. `OVERVIEW.md` 至少应包含以下板块：
   - 项目简介
   - 当前活跃事项表
   - 最近一次会话摘要
   - 下一步建议
   - 已知阻塞
2. 当前活跃事项表至少应包含：
   - `feature_id`
   - 标题
   - 状态
   - 最近更新时间
   - 下一步
   - 关键文件
   - 正式文档路径（若已存在）
3. Skill 更新 `OVERVIEW.md` 时，应只更新指定标记块，不应依赖脆弱的标题正则替换。
4. `OVERVIEW.md` 必须支持 round-trip，即未更新区域内容保持不变。

---

### 需求 6：生成功能轻量说明卡片

**用户故事：** 作为开发者，我希望在某个功能推进过程中维护一份简短但稳定的说明卡片，以便快速恢复上下文，而不把跟踪目录变成大型文档仓库。

#### 验收标准

1. Skill 必须支持在 `docs/project-tracker/features/` 下生成轻量功能说明卡片。
2. 轻量说明卡片至少应包含：
   - 功能标题
   - 功能 ID
   - 更新时间
   - 背景
   - 当前实现摘要
   - 关键文件
   - 风险或已知问题
   - 后续建议
3. 若同名卡片已存在，则应更新同一个文件，而不是生成大量重复文件。
4. 轻量说明卡片应保持简洁，不承担完整模块文档职责。

---

### 需求 7：提升为正式文档

**用户故事：** 作为开发者，我希望当某个功能完整做好后，AI 能把已有的代码、spec 和 tracker note 提升为一份正式模块文档，同时复用现有的 `professional-markdown` skill，而不是在 tracker skill 里重复造一套长文档能力。

#### 验收标准

1. Skill 必须支持 `promote-to-doc` 工作流，用于把某个成熟功能提升为正式文档。
2. `promote-to-doc` 必须优先复用 `professional-markdown`，而不是新增长文档 Python 生成脚本。
3. 正式文档默认应生成到 `docs/modules/`，除非用户指定其他文档目录。
4. Skill 必须支持基于现有代码和 tracker notes 批量选择多个成熟功能，交给 `professional-markdown` 生成正式文档。
5. 正式文档生成后，tracker 中对应的轻量卡片应保留，并补充正式文档链接。

---

### 需求 8：状态查询与恢复上下文

**用户故事：** 作为开发者，我希望在一段时间后快速恢复项目上下文，而不必重新翻所有代码和聊天记录。

#### 验收标准

1. Skill 必须支持输出项目概览和最近若干条进展记录。
2. Skill 必须支持按功能 ID 或关键词筛选相关进展记录。
3. Skill 查询状态时，应优先返回对恢复上下文最有帮助的信息，而不是原样倾倒全部文档。
4. 若项目未初始化，应返回明确提示并建议先执行初始化流程。

---

### 需求 9：Automation/周期性跟进兼容

**用户故事：** 作为开发者，我希望未来可以把这个 skill 接到自动化流程中，定期整理项目状态，而不是永远依赖手动触发。

#### 验收标准

1. Skill 设计必须允许被 automation 或定时任务调用。
2. Skill 在自动运行时，必须支持“无人工补充信息”的降级模式，即只基于仓库证据写入保守摘要。
3. 自动运行时若证据不足，应记录“待确认”，而不是输出高置信度结论。
4. Skill 文档中必须说明：仅有 skill 不等于持续跟进，还需要外部触发机制。

---

### 需求 10：实现约束

**用户故事：** 作为开发者，我希望 skill 的实现足够轻量、可维护，并能和现有项目结构兼容。

#### 验收标准

1. Skill 必须采用标准 skill 目录结构：`SKILL.md`、`scripts/`、`references/`。
2. `scripts/` 中的辅助脚本应尽量使用 Python 标准库，降低依赖复杂度。
3. Script 负责文件初始化和稳定写入，复杂判断仍由 Skill 工作流承担。
4. Skill 默认不得自动改写项目的 AI 规则文件。
5. Skill 应优先使用 UTF-8 编码读写跟踪文档。
6. 正式长文档生成必须通过 `professional-markdown` 完成，而不是通过 `project_tracker.py` 直接拼接输出。
