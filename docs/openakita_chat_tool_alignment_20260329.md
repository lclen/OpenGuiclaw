# 聊天 / 工具调用对齐 OpenAkita（阶段一 ~ 阶段二）

## 本轮完成

本轮没有直接引入多 Agent，而是先补齐两项最关键的基础能力：

1. **工具调用真正受 Agent Profile 约束**
2. **同步聊天复用流式运行链**

这两项是后续继续对齐 OpenAkita 的前置条件。

在此基础上，又补了一层 **轻量工具路由**：

3. **用三层记忆驱动工具排序**

继续往前推进后，本轮又补了两项更接近 OpenAkita 的能力：

4. **工作区记忆作用域路由**
5. **ChatRuntime 对工作区上下文的统一透传**
6. **会话摘要 / 工具历史 / 记忆召回统一装配**

---

## 1. 工具调用按 Profile 真正隔离

过去的问题：

- `allowed_skills` / `skills_mode` 已经存在
- 但 `SkillManager.get_tool_definitions()` 仍然把全部启用工具暴露给模型
- 导致 Profile 更像“提示词偏好”，而不是“真实能力边界”

本轮调整后：

- `core/skills.py` 新增可见性判定
- 工具暴露支持：
  - `all`
  - `inclusive`
  - `exclusive`
- 匹配维度支持：
  - skill name
  - category
  - plugin_name
  - source_type
- 内置核心工具（`builtin_skill`）默认始终可见，避免基础交互能力被误伤

这样做的效果是：

- Profile 不再只是 UI 概念
- 工具边界开始接近 OpenAkita 的 Profile 驱动模式

---

## 2. 同步聊天改为复用流式运行链

过去的问题：

- `chat()` 和 `chat_stream()` 是两套独立运行逻辑
- 同步路由直接走 `agent.chat()`
- 流式路由走 `agent.chat_stream()`
- 后续一旦继续增强工具规划、回滚、记忆注入，就会产生双份维护成本

本轮调整后：

- `POST /api/chat/sync` 优先复用 `agent.chat_stream()`
- 同步接口会聚合 `text_delta` 输出为最终文本
- 若 Agent 没有 `chat_stream()`，仍回退到旧 `chat()`

这意味着：

- 至少桌面主聊天入口的 sync / stream 开始共享同一条主执行链
- 后续继续统一 `chat()` 本体时，改造成本明显更低

现在 `Agent.chat()` 本体也已经转为复用 `chat_stream()` 聚合结果，而不是维护一套独立工具循环。

---

## 3. 工具路由开始接入三层记忆

本轮新增的是“轻量路由”，不是完整 Planner：

- 读取当前可见工具集
- 用查询文本命中、外挂技能命中、偏好层记忆、经验层记忆做打分
- 对工具定义进行重排，让更适合的工具优先暴露给模型
- 同时在系统提示中插入“工具路由提示”

这样做的效果是：

- 经验层记忆开始影响“优先用什么工具”
- 偏好层记忆开始影响“什么工具更符合用户长期习惯”
- 为后续真正的 Planner / ChatRuntime 铺路

---

## 4. 工作区记忆开始进入主链路

本轮新增了工作区记忆作用域：

- `MemoryItem` 增加：
  - `workspace_id`
  - `workspace_name`
- 记忆写入时会优先继承当前自动化/聊天上下文里的工作区信息
- 记忆检索采用：
  - **先查当前工作区**
  - **不足时回填全局记忆**
  - **不再把其它工作区的经验混进当前工作区**

这样做的效果是：

- 当前项目里的经验不会轻易污染另一个项目
- 又不会丢掉真正通用的全局偏好和全局经验
- 这已经开始接近 OpenAkita 那种“工作区驱动记忆召回”的体验

---

## 5. ChatRuntime 开始统一工作区上下文

这次还顺手补齐了聊天运行时的上下文透传：

- `chat_stream()` 会先统一解析当前工作区上下文
- `_build_system_prompt()`、`_build_tool_routing_plan()`、三层记忆注入都共用同一份工作区上下文
- `/api/chat/sync` 也会从当前 session 元数据里透传工作区上下文
- workspace fallback 路径里的工具路由同样拿到工作区信息

这意味着：

- prompt、工具排序、记忆召回不再各走各路
- “聊天 / 工具 / 记忆” 三条链路开始围绕同一个 workspace context 收敛

---

## 6. 会话摘要 / 工具历史 / 记忆召回统一装配

本轮继续往 OpenAkita 靠拢，新增了一个轻量的运行时上下文装配器：

- `Agent._assemble_runtime_context(...)`

它会在真正发起模型请求前，一次性收敛：

- 当前工作区上下文
- 当前会话滚动摘要
- 最近工具调用脉络
- 最近视觉背景
- 三层记忆召回结果
- 工具路由结果
- 裁剪后的历史消息

这次调整的关键点有两个：

1. `Session.get_history()` 新增 `include_summary=False`
2. 会话摘要不再只靠“伪造 user/assistant 历史消息”混进上下文，而是可以作为系统级上下文块统一注入

这样做的效果是：

- prompt 组装更清晰，不再把摘要、工具历史、记忆分散塞在不同层
- `chat_stream()` 主链路只做一次上下文准备，避免重复检索和重复路由
- workspace fallback 旧路径也可以复用同一份运行时上下文

这一步非常像 OpenAkita 的做法：

- 先组装 runtime context
- 再把 context 投喂给单一聊天执行器
- 而不是让每个功能点各自临时往 prompt 里拼字符串

---

## 为什么这一步很重要

OpenAkita 的强项不只是模块多，而是：

- Profile 真正约束能力边界
- 运行链尽量收敛到单一执行主线
- 记忆、工具、规划能稳定插入同一个闭环

如果不先解决这两点，后续再加：

- Planner
- 多 Agent 委派
- 工作区经验记忆
- 技能 SOP 路由

都会继续叠加在松散的基础上，越改越难收敛。

---

## 下一阶段建议

下一步最值得做的是：

1. 抽出独立的 `ChatRuntime / ToolRuntime` 类，彻底从 `Agent` 中解耦
2. 让 workspace fallback 路径完全复用同一执行器，而不是保留半套旧流程
3. 给运行时上下文增加“任务阶段 / 当前目标 / 最近失败原因”字段，增强多轮自修复
4. 把工作区经验记忆继续细化为“全局偏好 + 工作区经验 + 当前任务上下文”
